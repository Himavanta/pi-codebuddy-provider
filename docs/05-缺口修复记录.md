## #6 refresh token 请求头（`232ea18`）

### 问题

`refreshAccessToken` 用 `Authorization: Bearer <refreshToken>` 发送，但上游只读
`X-Refresh-Token`。导致三条刷新路径（Pi 原生预刷新 / `oauth.refreshToken` /
auth-fetch 401 兜底）全部失效。

### 实测证据

真实端点 `copilot.tencent.com`（假 token，2026-10-11）：

```
Authorization: Bearer <token>  → 400 {"code":10001,"msg":"10001:refreshToken is empty"}
X-Refresh-Token: <token>       → 401 {"code":12153,"msg":"refresh token failed:10000:token format error"}
```

后者返回「token format error」而非「empty」，证明服务端确实读取了 `X-Refresh-Token`。

### 修复

```ts
{ method:"POST", headers:{ "Content-Type":"application/json", Accept:"application/json",
    "X-Refresh-Token": refreshToken, "X-Auth-Refresh-Source": "plugin" }, timeoutMs: REFRESH_TIMEOUT_MS }
```

与 opencode 版 `8c52c4c` 对齐（含 `X-Auth-Refresh-Source: plugin`）。

### 测试

新增 `test/auth-flow.test.ts`（pi 版此前无此模块测试），17 个用例覆盖
`requestAuthState` / `pollForToken` / `refreshAccessToken`，含：

- 「带 `X-Refresh-Token` 头（不是 `Authorization`）」，断言 `Authorization` 为 `undefined`
- 「透传轮换后的 refreshToken 与 expiresIn」
- 「带 `X-Auth-Refresh-Source: plugin`」

## #3 reasoning_content 兜底（`11808a5`）

### 问题

带 `tools` 的请求要求历史 assistant 消息回传 `reasoning_content`，但部分模型可跳过
推理（`canDisableThinking`）→ 无内容可回传 → 上游返回 400（`code 11155`）。
opencode 版在 `auth-fetch` 里手工遍历 messages 补空串；pi 版两层都缺失。

### 方案选择

pi-ai 已有原生开关 `compat.requiresReasoningContentOnAssistantMessages`
（`api/openai-completions.js:1047`），无需手改 body。实测其行为：

```
compat=true  + model.reasoning=true  → assistant 带 reasoning_content:""   ✅
compat=true  + model.reasoning=false → 不补（依赖 model.reasoning）
compat=false + model.reasoning=true  → 不补
```

且它仅在 `reasoning_content === undefined` 时补空串，**不覆盖已有 thinking 内容**。

**决策**：采用 pi-ai 原生方案（比 opencode 的 body 注入更干净），不额外做 body 注入。

### 修复

```ts
compat: { supportsDeveloperRole: false, requiresReasoningContentOnAssistantMessages: true },
```

注意其生效依赖 `model.reasoning === true`，故必须与 #2（`supportsReasoning` 修复）配合。

### 测试

3 个用例：标志存在性、非推理模型行为、端到端（经 `onPayload` 捕获请求体验证补空串）。

## #4 thinkingLevelMap 语义（`723beef`）

### 问题

原实现两处错误：

```ts
cfg.thinkingLevelMap = Object.fromEntries(efforts.map((e) => [e, e])) // 键用上游档名
if (effort) cfg.thinkingLevelMap.default = effort // default 不是合法键
```

pi 的契约（`types.d.ts` + `models.js::getSupportedThinkingLevels`）：

- 档位是固定集合 `off|minimal|low|medium|high|xhigh|max`
- `thinkingLevelMap` 是「pi 档位 → 上游取值」映射，**键必须是 pi 档位**
- `minimal/low/medium/high` **默认全部包含**，除非显式 `null`
- `xhigh`/`max` 必须在 map 中有条目才可见
- 不存在 `default` 键

### 后果

上游只支持 `low/high` 的模型（`hy3` 等）会在 UI 暴露 `medium` 档，用户选中后原样发出
`reasoning_effort: "medium"`（上游不支持的值）；`glm-5.2`（仅 `high/xhigh`）会暴露
`low/medium`；`xhigh`/`max` 又因键名问题不可见。

### 依据

pi 官方模型目录惯例（`dist/providers/data/*.json`，773 个含 `thinkingLevelMap` 的样例）：

```json
// 全档位（anthropic claude-haiku-5-5）
{"off": null, "minimal": null, "low": "low", "medium": "medium", "high": "high", "xhigh": "xhigh", "max": "max"}
// 仅部分档位（amazon-bedrock claude-haiku-5-5）
{"xhigh": "xhigh", "max": "max"}
// 仅 off（azure gpt-5）
{"off": null}
```

即：**只列需要声明的档位，不支持的写 `null`**。

### 修复

新增 `buildThinkingLevelMap(m)`：

- 不支持的标准档位显式写 `null`（移出可选集合）
- `xhigh`/`max` 仅在支持时写入（无条目即不可见）
- `canDisableThinking` 决定 `off` 是否可选（`false` 或字段缺失 → `null`）
- 无 `supportedEfforts` 时返回 `undefined`（交给 pi 默认，且不发 `reasoning_effort`）

同时 `RemoteModel.reasoning` 补 `canDisableThinking` 字段。

### 真实验证

`/v3/config` craft 13 个模型的可选档位与实际发送值：

| 模型                                            | 可见档位                            | 发送 `reasoning_effort`                     |
| ----------------------------------------------- | ----------------------------------- | ------------------------------------------- |
| `hy4-preview-f`                                 | `high`                              | `high`                                      |
| `hy3` / `hy3-x`                                 | `low` `high`                        | 对应                                        |
| `space-bunny`                                   | `low` `medium` `high` `xhigh` `max` | 对应                                        |
| `deepseek-v4.1-flash`                           | `low` `high` `max`                  | 对应                                        |
| `deepseek-v4-pro`                               | `low` `high` `xhigh`                | 对应                                        |
| `glm-5.3` / `glm-5.3-flash`                     | `low` `high` `max`                  | 对应                                        |
| `glm-5.2`                                       | `high` `xhigh`                      | 对应                                        |
| `auto` / `glm-5.1` / `kimi-k3-1` / `minimax-m3` | 默认标准档（无词表）                | 不发字段（`supportsReasoningEffort:false`） |

全部模型的可见档位严格等于上游 `supportedEfforts`。

### 关于默认档

上游的 `defaultEffort` / `effort` 是元数据，pi 侧**无对应字段**可用于表达「模型默认档」
（已确认 pi 无 `defaultThinkingLevel`）；默认档由用户的 pi 思考设置决定，
经 `clampThinkingLevel` 归一到该模型的可用档位。故本次不再写入任何 `default` 键。

### 测试

6 个 `buildThinkingLevelMap` 专项用例 + 更新 2 个既有断言（移除无效 `default` 键期望）。

## #5 contextWindow 对象形态（`48dc2ae`）

### 问题

上游容量字段有两种形态：

- 数字：`maxAllowedSize` / `maxInputTokens`（5 个模型）
- 对象：`contextWindow = { defaultLength, supportedLengths }`（7 个模型，如
  `space-bunny` / `deepseek-v4*` / `glm-5.2~5.3` / `minimax-m3`）

原实现只读前者，对象形态被完全忽略。当前因这些模型的 `maxAllowedSize` 恰好等于
`supportedLengths` 最大值而未暴露，属健壮性缺口（opencode 版同样未处理）。

### 修复

新增 `resolveContextWindow(m)`：

- 对象形态取 `supportedLengths` 最大值（与 `maxAllowedSize` 语义一致）
- 只有 `defaultLength` 时回退到它
- 非法/空值回退 `maxAllowedSize` / `maxInputTokens` / `DEFAULT_CONTEXT`
- 对象显式声明上下文长度，优先于通用的 `maxAllowedSize`

同时 `RemoteModel` 补 `contextWindow` 字段。

### 真实验证

craft 13 个模型的解析结果与修复前**完全一致**（`changed=0`），纯健壮性修复。

### 待定

另一种可选解读：取 `defaultLength`（上游默认档，实测 `300000`），会让 pi 更早触发
自动压缩（阈值 = `contextWindow - reserveTokens`）、降低每轮重发 token 量。
但这会**改变现有行为**，且 PR #4 作者在讨论中倾向「插件不该自作主张改这个值」
（上游上报的 `maxAllowedSize` 本身是对的，问题在于 `maxAllowedSize` 语义不统一）。

保留现状（最大值），如需切换见 `03-执行计划.md` 待决事项。

### 测试

4 个用例：取值、优先于 `maxAllowedSize`、仅 `defaultLength` 回退、非法值回退。

## 后续修正：#4 关于默认档的两处判断有误

日期：2026-10-12
commit：`c45c884`

### 被修正的结论

上文 #4 的「关于默认档」与「真实验证」表格中，两处判断后来被实测推翻：

1. 「上游的 `effort` 是元数据，pi 侧**无对应字段**可用于表达」
2. 「`auto` / `glm-5.1` / `kimi-k3-1` / `minimax-m3` 不发字段」

### 为什么错

第 1 点在第 2 点被推翻后站不住：既然这些模型必须收到一个 `reasoning_effort`，
那 `effort`（上游声明的档位值）就是可用的信息，而 pi 的 `thinkingLevelMap`
**能**表达它——把 `off` 与其余档位置 `null`、把该档映射为自身即可。

### 实测证据

| 模型         | 不发 `reasoning_effort` | 发 `medium` |
| ------------ | ----------------------- | ----------- |
| `glm-5.1`    | **400**（code 11150）   | 200         |
| `kimi-k3-1`  | 200                     | 200         |
| `minimax-m3` | 200                     | 200         |
| `auto`       | 200                     | 200         |

`glm-5.1` 的 400 稳定复现（5/5 次），且带完整 payload（tools / temperature /
max_tokens）时同样复现；非空 effort 值均返回 200。

上游报错文案是
`the reasoning effort value is not supported by the current model`，但实际含义是
「**必须给一个值**」——与字面相反。

### 另一个发现：`off` 档才是真正的难点

pi-ai 在用户档位为 `off` 时**不带** `reasoning_effort`：

```js
// pi-ai openai-completions.js:525
const reasoningEffort = clampedReasoning === 'off' ? undefined : clampedReasoning
```

因此仅把 `supportsReasoningEffort` 置回默认是不够的：用户切到 `off` 时仍会回到
400。必须把 `off` 显式置 `null`（移出可选集合），再由 `clampThinkingLevel`
把任何用户档位归到该模型唯一的档位。

### 修正后的行为

`buildThinkingLevelMap` 在无 `supportedEfforts` 时用 `effort` 单档兜底，
且「只有 effort」时一律移除 `off`（上游未声明可关闭思考）。

| 模型        | 上游声明           | 可用档位     | 实际发出         |
| ----------- | ------------------ | ------------ | ---------------- |
| `glm-5.1`   | 仅 `effort=medium` | `medium`     | `medium`         |
| `auto`      | 仅 `effort=high`   | `high`       | `high`           |
| `kimi-k3-1` | 仅 `effort=medium` | `medium`     | `medium`         |
| `hy3`       | 词表 `low/high`    | `low` `high` | 对应（词表优先） |

端到端验证：`glm-5.1` 的用户档位 `off` / `minimal` / `low` / `medium` / `high` /
`xhigh` / `max` **全部**钳到 `medium`，实际发出 `reasoning_effort: "medium"`。

### 附带更正

`docs/07` 曾据「本地静态表」解释模型列表差异，该前提也不成立
（真实原因是 UA），见该文档的修订说明。

## 后续修正（2026-10-15）：模型发现警告糊在输入框

用户报告：更新扩展后，开启代理再打开 pi，输入框里会出现
「model discovery 失败，沿用现有模型列表」的警告。经查这是**两个独立问题**。

### 问题一：警告直写 stderr 破坏 TUI

`log.ts` 的 `warn` / `error` 走 `console.error`。但 pi 只接管 **stdout**，且**仅在
非交互模式**：

```js
// main.js:522
const shouldTakeOverStdout = appMode !== "interactive" && ...
```

且没有 `takeOverStderr`。交互模式（默认 `fullscreen`，走备用屏）下 stderr 无人接管，
`console.error` 的字节能直接落到光标处 —— 表现就是警告糊在输入框上。

pi 有正规的非阻塞反馈通道 `ctx.ui.notify()`（`docs/tui.md`：「非阻塞反馈 →
`ctx.ui.notify()` 或 `setStatus()`」）。约束是 **`ctx.ui` 只存在于事件 handler**，
`ExtensionAPI`（工厂收到的 `pi`）上没有 `ui`。

修法：`log.ts` 新增 `bindUI(ui)` / `silence()`，由 `index.ts` 在 `session_start`
绑定、`session_shutdown` 静默。绑定后走 `notify`，未绑定（print / JSON 模式，
`hasUI=false`）回退 console。**一处改动修掉整类问题**（`reasoning-leak` 的 warn 同样会糊屏）。

### 问题二：发现请求跑在 5s 超时线上

实测（真实凭据、直连 `/v3/config`）：

```
连测 6 次：第1次❌ 第2次4361ms 第3次3026ms 第4次❌ 第5次❌ 第6次❌
curl 分解：DNS 0.003s / TCP 0.41s / TLS 1.0~1.7s / 总计 2.2~4.4s
```

TLS 握手即占 1~1.8s，端到端贴着 `DISCOVERY_TIMEOUT_MS = 5000` 反复横跳，**6 次里 4 次超时**。
且**没有重试**，`DiscoveryCache` 失败后要等 5min TTL 才重试。

修法：超时 5000 → **15000**（与 pi 自身的模型目录刷新一致，`interactive-mode.js` 用 `15_000`）。
**不加重试**——失败即沿用本地缓存，下次启动或 `/reload` 会重来。

### 顺带：改为后台发现，不阻塞启动

`docs/tui.md` 建议「不要在 factory 里启动异步资源」。且 pi 自己在交互式启动时已在后台
刷新模型目录（`interactive-mode.js:833`，`void refreshModelCatalogs(...)` + 15s 超时），
那条链最终也会调用本扩展的 `refreshModels`。

改为：

| 场景                   | 行为                                                                                   |
| ---------------------- | -------------------------------------------------------------------------------------- |
| 有落盘缓存             | 工厂不 await，立即返回；`session_start` 里后台发现                                     |
| **无落盘缓存（首次）** | 工厂 **await** 一次 —— 否则 `--list-models` 这类短命进程会在响应前退出，缓存永远写不进 |
| 会话结束               | `session_shutdown` 递增 `sessionGen` + `logger.silence()`                              |

`sessionGen` 用于丢弃上一个会话遗留的后台发现回调 —— 否则 `/reload` 前发起的发现会在
新会话里重新注册模型，并在 `ctx` 失效后输出提示。

### 关于 `/reload`

`/reload` 会重跑扩展工厂，因此能重新读盘：

```
/reload → session.reload() → resourceLoader.reload()
        → clearExtensionCache()                      (extensions/loader.js:89)
        → initializeExtension() → await factory(...) (extensions/loader.js:514)
        → emit session_start { reason: "reload" }    (agent-session.js:2998)
```

`session_shutdown` 的 `reason` 含 `reload`，与 `quit` / `new` / `resume` / `fork` 共用同一处理。

### 验证

`vp test` **184 通过**（新增 `test/log.test.ts` 6 例）；`vp check` 0 error。

故意破坏验证：把 `bindUI` 分支的 `return` 去掉 → 1 例失败；把 `silence()` 改成只清 `ui`
不清 `silent` → 1 例失败。

真实路径实测（`pi -e ./src/index.ts`，带插桩确认走了预期分支）：

```
有缓存 + --list-models : 0.55s，不阻塞
无缓存 + --list-models : await 发现 → 15 个 → 写缓存
--print（有缓存）       : session_start hasUI=false → 后台发现 283ms
```

（最初几次 `pi --list-models` 验证跑的是旧代码，结论无效，后已重做。）
