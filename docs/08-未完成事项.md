## 1. 换 CLI 型 UA 拿更多模型列表

**现状**：未做。`src/models.ts:81` 的发现请求仍用 IDE 型 UA，
`grep "CLI/" src/` 无结果。

**背景**：`07` 已查明模型列表差异的真正原因是 `User-Agent`，
不是数据源缺失。同凭据同端点：

| UA             | agents | models | 清单          |
| -------------- | ------ | ------ | ------------- |
| IDE 型（当前） | 15     | 22     | `craft` 15 个 |
| CLI 型         | 1      | 33     | `cli` 18 个   |

**收益**：多 4 个模型（实测全部可用）：

```

```

**方案选择**：

| 方案                | 改动                | 风险               |
| ------------------- | ------------------- | ------------------ |
| ① 只改发现请求的 UA | 仅 `GET /v3/config` | 低（聊天链路不动） |
| ② 发现 + 聊天都改   | 整条链路            | 高（要重新验证）   |

前提已变，此事**尚无定论**。

**替代方案**：不改代码，按需用 `CODEBUDDY_MODEL`：

## 2. 错误文案未用上游 `displayMsg`

上游每个错误都返回中英双语可读提示：

```json
{
  "code": 11151,
  "msg": "a message has empty content, please check the conversation history and retry",
  "requestId": "…",
  "displayMsg": { "en": "Invalid request. Please retry", "zh": "请求内容不合法，请重试" }
}
```

`grep displayMsg src/` 无结果——**完全未使用**。用户看到的是英文 `msg`。

**影响**：中英混杂，缺少针对性提示。例如 `11140` 的 `displayMsg`
是「账号存在异常行为，已被限制使用」，比 `msg` 清楚。

**位置**：`src/auth-fetch.ts` 的 `normalizeErrorResponse`。

## 3. 429 未识别额度耗尽（`14018`）

**现状**：终态判定只看 `Retry-After` 时长：

```ts
const terminal =
  current.status === 429 && (hintMs === undefined ? false : hintMs > cfg.rateLimitMaxWaitMs)
```

额度耗尽的 429（`14018 Credits exhausted`）若不带 `Retry-After`，
会被**当成普通限流重试**，白等。

**依据**：Magpie（`internal/gateway/routing.go`）专门用正则识别：

```go
brokeWords = regexp.MustCompile(`(?i)insufficient.?(balance|credit|fund)|…|\bcredits? (are )?exhausted\b|…`)
```

**注意**：`14018` 本次**未能实测触发**（需额度耗尽），依据为 Magpie 的记录，
属二手来源。

## 6. 401 的 HTML 响应体原样透传

token 完全无效且刷新失败时，网关前置代理返回 HTML 而非 JSON：

```
HTTP 401 Authorization Required
<html><head><title>401 Authorization Required</title></head>…
```

`normalizeErrorResponse` 会原样透传，pi-ai 把 HTML 塞进 error body。

**罕见**（需 token 无效 + 刷新失败同时发生），但体验差。
