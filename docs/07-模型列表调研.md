# 模型列表调研

日期：2026-10-12（2026-10-14 修订）
起因：Pi 里的模型列表少于 CodeBuddy IDE / CLI 显示的。
结论：**不额外补列表**——差异的真正原因是请求的 `User-Agent`，不是数据源缺失；
保留 `CODEBUDDY_MODEL` 作为逃生通道。

> **修订说明**：本文初版把差异归因于「部分模型只在官方 CLI 的本地静态表里，
> 接口不返回」，并据此提出「读取 CLI 本地文件」的方案。该前提经复测**不成立**：
> 这些模型 `/v3/config` 会返回，只是需要 CLI 型 `User-Agent`。初版结论已作废，
> 下文按新证据重写；仍成立的部分（第二节的端点事实、第三节的字段规律）保留。

## 一、现象

| 来源                                                | 模型数 |
| --------------------------------------------------- | ------ |
| 上游 `/v3/config`，IDE 型 UA，`models` 总数         | 22     |
| 上游 `/v3/config`，IDE 型 UA，分给 `craft` agent 的 | 15     |
| 上游 `/v3/config`，CLI 型 UA，`models` 总数         | 33     |
| 上游 `/v3/config`，CLI 型 UA，分给 `cli` agent 的   | 18     |

本扩展用 IDE 型 UA 取 `craft` 列表，因此拿到 15 个。

## 二、根本原因：`User-Agent` 决定返回哪个产品的配置

同一个凭据、同一个 `/v3/config`，只改 `User-Agent`，返回的是**不同产品的配置**：

| `User-Agent`                            | agents | `models` 总数 | `craft` | `cli` |
| --------------------------------------- | ------ | ------------- | ------- | ----- |
| `VSCode/1.119.0 CodeBuddy/4.9.29177644` | 15     | 22            | 15      | —     |
| `CLI/2.164.0 CodeBuddy/2.164.0`         | 1      | 33            | —       | 18    |
| `CLI/2.0.0 WorkBuddy/5.5.6`             | 1      | 60            | —       | 18    |
| `WorkBuddy/5.5.6`（裸）                 | 14     | 37            | 10      | —     |

要点：

- **IDE 型 UA** → 返回 15 个 agent（`craft` / `ask` / `plan` / `CodeCompletion`…），
  没有 `cli` agent
- **CLI 型 UA** → 只返回一个 `cli` agent，`models` 数从 22 升到 33
- **`X-Agent-Intent` 头对 `/v3/config` 无效**：设为 `craft` / `cli` / 不设，
  返回的 agent 列表完全相同（只由 UA 决定）

Magpie（`yetone/magpie`）的注释也记了这条，其做法是**发现用 CLI 型 UA、
聊天用 WorkBuddy 型 UA**：

```go
// internal/provider/workbuddy_models.go
req.Header.Set("User-Agent", "CLI/"+wbAppVersion+" WorkBuddy/"+wbUAVersion)
```

### `craft` 15 个 vs `cli` 18 个

二者交集 14 个，各自独有：

- 仅 `craft`：`auto`
- 仅 `cli`：`glm-5v-turbo`、`kimi-k2.6`、`kimi-k2.7`、`minimax-m2.7`

初版认为这 4 个「接口不返回」，实际是**用 IDE 型 UA 时不返回**。

### `models` 数组的差集

| 方向   | 数量 | 内容                                                                                                       |
| ------ | ---- | ---------------------------------------------------------------------------------------------------------- |
| 仅 IDE | 6    | `auto`、`codewise-completions`、`codewise-default-model-v2`、`codewise-jump`、`codewise-rewrite`、`nes-gf` |
| 仅 CLI | 17   | `glm-4.6`、`glm-5.0`、`hunyuan-chat`、`kimi-k2.5`、`hy4-preview-x` 等                                      |

IDE 独有的多为非对话模型（代码补全、NES），CLI 独有的含多代旧模型。

## 三、已确认的端点事实

### 网关按请求体的 `model` 字段选模型

| 请求体 `model` | `X-Model-ID` 头 | 服务端回显     |
| -------------- | --------------- | -------------- |
| `hy3`          | `glm-5v-turbo`  | `hy3`          |
| `glm-5v-turbo` | `hy3`           | `glm-5v-turbo` |

`X-Model-ID` 不参与模型选择。这解释了 `CODEBUDDY_MODEL` 原先为何无效——它只改头，
已在 `dabdc15` 修复为覆写请求体。

### 网关只支持流式请求

非流式返回 `400 code 11101`
（"Non-stream chat request is currently not supported"）。

### `reasoning_effort` 的取值不被校验

发任意非空字符串（含 `banana`）都返回 200；空值与 `none` 在部分模型上返回
`400 code 11150`。详见 `docs/05` 的「后续修正」一节。

### 发现可用 ≠ 调用可用

用 CLI 型 UA 发现的 17 个「仅 CLI」模型中，只有 10 个能用 IDE 型 UA 调用：

```
可用：   deepseek-v3-2-volc, default, glm-5.0, glm-5.0-turbo, glm-5v-turbo,
         hunyuan-chat, kimi-k2.5, kimi-k2.6, kimi-k2.7, minimax-m2.7
不可用： glm-4.6, glm-4.6v, glm-4.7, hunyuan-image-alpha-edit,
         hy4-preview-x, kimi-k2-thinking, minimax-m2.5
```

不可用的多报 `code 11102`（`model [...] service info not found`）：`glm-4.6`、
`glm-4.6v`、`glm-4.7`、`hy4-preview-x`、`kimi-k2-thinking`、`minimax-m2.5`；
`hunyuan-image-alpha-edit` 例外，报 `11103`（`Backend [hunyuan-stream] is not supported`，
图像模型不走 chat 通道）。

`modelTiers` 字段里还出现过 `claude-opus-4.8`、`echo`，两者均**不可用**
（`400`，且不在 `models` 数组内）。

## 四、官方 CLI 的模型来源（供参考）

官方 CLI **不请求** `/v3/config` 取模型，而是读自身包内的 `product.*.json`：

| 文件                       | 模型数 | endpoint                      |
| -------------------------- | ------ | ----------------------------- |
| `product.json`             | 22     | `https://www.codebuddy.ai`    |
| `product.internal.json`    | 32     | `https://copilot.tencent.com` |
| `product.ioa.json`         | 53     | `https://copilot.tencent.com` |
| `product.cloudhosted.json` | 22     | 无                            |
| `product.selfhosted.json`  | 1      | 无                            |

文件位置：`{全局 node_modules}/@tencent-ai/codebuddy-code/product.*.json`。
注意：**不在** `~/.codebuddy/`（那里只有 settings、日志、插件等用户数据）。

CLI 还会调用企业自定义模型接口：

```
GET {endpoint}/console/enterprises/{enterpriseId}/config/models
```

实测（本次账号，`enterpriseId` 取自 JWT 的 `enterprise_id`）：

```
HTTP 200，data 为空数组
```

CLI 代码在响应为空时回退到本地静态表：

```js
if (!response.data.data.length) {
  return this.getFallbackResult() // 本地 product.*.json
}
```

本地静态表的 `reasoning` 形态与服务端不同，且更适合做单挡推断：

- 20 个模型只有 `{effort, summary}`（无 `supportedEfforts`）
- 5 个有 `supportedEfforts`：`glm-5.3-flash`、`glm-5.3-flashx`、
  `kimi-k2.8-preview`、`hy4-preview`、`hy4-preview-x`

**因为 `/v3/config` 用 CLI 型 UA 就能拿到更全的列表，读本地文件已无必要。**

## 五、为什么最终仍不补列表

既然换 UA 就能拿到 18 个，为什么不改？

1. **改 UA 会改变整个请求形状**。`craft` 是 IDE 的 agent 意图，本扩展模仿的是
   IDE 客户端；切到 CLI 型 UA 后 `X-Agent-Intent`、`X-IDE-Type` 等头与实际身份
   不再自洽，需要整体重新验证。
2. **多出来的模型未必可用**。上节实测：17 个「仅 CLI」模型中只有 10 个能调用，
   其中 4 个（`glm-5v-turbo`/`kimi-k2.6`/`kimi-k2.7`/`minimax-m2.7`）是那 4 个差集，
   其余 6 个（`glm-5.0`、`hunyuan-chat`、`kimi-k2.5` 等）是旧型号，价值有限。
3. **收益是 4 个模型，成本是重新验证发现与调用两条链路**，且要处理「发现得到但
   调用不了」的模型（会让 Pi 里出现选中即 400 的条目）。

需要这些模型时的替代路径见下节。

## 六、现状与替代方案

1. **`CODEBUDDY_MODEL`** — 直接指定任意模型 ID（`dabdc15` 起已生效）。
   需要 `glm-5v-turbo`、`kimi-k2.6` 等模型时用它。
2. **`~/.pi/agent/models.json`** — 需要出现在 Pi 模型选择器里时使用。
   按 Pi 文档，`models` 条目会在该 provider 上新增（或替换同 ID 的）模型，
   且早于扩展注册应用，因此新增的 ID 不会被后续发现覆盖。

注意：本扩展**刻意不写** `models.json`（见 `src/model-cache.ts` 头部注释）——
鉴权由 fetch 拦截器注入，在 `models.json` 里声明原生 provider 会引入
`baseUrl`/`api` 的重复定义。应由使用者自行添加，不由扩展代劳。

## 七、若将来要实现

> **本节已于 2026-10-14 复核并更正**，完整实测见
> [09-换用CLI型UA的评估记录.md](./09-换用CLI型UA的评估记录.md)。
> 该次评估的结论是**放弃**：换 UA 的代价（5 个模型档位退化、7 个模型输出上限
> 缩水、丢失 `auto`）超出 4 个新模型的收益。

以下为更正后的要点：

1. UA 只影响**发现请求**（`GET /v3/config`）。实测那 4 个差集模型用 IDE 型 UA
   也能调用，故聊天链路是否跟进需另行权衡——但**链路身份不自洽本身是隐患**，
   上游若加一致性校验就会失效。
2. 取 `cli` agent 的模型清单，不要取 `models` 全量（后者含大量非对话模型）。
3. ~~对清单内的每个 ID 试调用一次再注册~~ **不需要**（本节原判断有误）：
   原结论出自 `models` 全量（33 个），而 `cli` 清单的 18 个实测 18/18 全部可用，
   且都有完整详情；不在清单里的模型本就不会被分派给用户。
4. 每个模型仍需从 `models` 数组取详情，两个列表按 ID 关联。
5. **必须逐字段对比元数据**，不要只看模型数量。CLI 侧对 5 个模型不给
   `supportedEfforts`（只给 `effort`），7 个模型的 `maxOutputTokens` 更小。
