日期：2026-10-12

结论：**不实现**从本地静态表补齐模型列表；保留 `CODEBUDDY_MODEL` 作为逃生通道。

- 网关**只支持流式**请求；非流式返回 `400 code 11101`
  （"Non-stream chat request is currently not supported"）
- 非对话模型（`codewise-completions`）即使出现在 `/v3/config` 里也不接受 chat 请求

## 实测：网关按 body 的 `model` 字段选模型

| 请求体 `model` | `X-Model-ID` 头 | 服务端回显     |
| -------------- | --------------- | -------------- |
| `hy3`          | `glm-5v-turbo`  | `hy3`          |
| `glm-5v-turbo` | `hy3`           | `glm-5v-turbo` |

**结论**：`X-Model-ID` 不参与模型选择。

这解释了 `CODEBUDDY_MODEL` 原先为何无效——它只改头。已在 `dabdc15` 修复为覆写请求体。

## 为什么没有实现「从本地静态表补齐」

### 障碍 1：`reasoning` 字段结构不同

同一模型 `hy3` 两侧的 `reasoning`：

```jsonc
// /v3/config
"reasoning": {
  "canDisableThinking": false,
  "defaultEffort": "high",
  "supportedEfforts": ["low", "high"]
}

// product.internal.json
"reasoning": { "effort": "high", "summary": "auto" }
```

生成 `thinkingLevelMap` 依赖 `supportedEfforts`。本地静态表中：

- 20 个模型只有 `{effort, summary}`——**无 `supportedEfforts`**
- 5 个有 `supportedEfforts`：`glm-5.3-flash`、`glm-5.3-flashx`、
  `kimi-k2.8-preview`、`hy4-preview`、`hy4-preview-x`

即从本地表补进来的模型会缺少思考档位信息。

### 障碍 2：把 CLI 作为依赖体积过大

`@tencent-ai/codebuddy-code` 解包后 **181 MB**（本地实测 208 MB）：

```
dist 87M, vendor 64M, node_modules 32M, dist-server 24M
```

而所需的 `product.*.json` 合计约 490 KB。为该文件强制安装 181 MB 不成比例。

### 障碍 3：可靠地定位包目录不易

- 全局 `node_modules` 路径随平台与包管理器而异（npm / pnpm / bun / nvm / Vite+ 托管 Node）
- 扩展运行在 pi 的模块上下文里，`require.resolve('@tencent-ai/codebuddy-code/package.json')` 失败
- 可行方案是「由 `PATH` 反查 `codebuddy` 可执行文件再解析软链」或「用户显式指定路径」，
  但仍有 5 个 `product.*.json` 需要按环境选择

## 现状与替代方案

不补列表，保留两条使用路径：

1. **`CODEBUDDY_MODEL`** — 直接指定任意模型 ID（`dabdc15` 起已生效）
2. **`~/.pi/agent/models.json`** — 需要出现在 Pi 模型选择器里时使用。
   按 Pi 文档，`models` 条目会在该 provider 上新增（或替换同 ID 的）模型，
   且早于扩展注册应用，因此新增的 ID 不会被后续发现覆盖。

注意：本扩展**刻意不写** `models.json`（见 `src/model-cache.ts` 头部注释）——
鉴权由 fetch 拦截器注入，在 `models.json` 里声明原生 provider 会引入
`baseUrl`/`api` 的重复定义。应由使用者自行添加，不由扩展代劳。

需要 `glm-5v-turbo`、`kimi-k2.6` 等模型时用第 1 条。

## 若将来要实现

调研结论可直接复用，需要注意的点：

1. 路径来源优先 `CODEBUDDY_CLI_PATH`，其次从 `PATH` 反查（不做全盘搜索）
2. 按 `CODEBUDDY_NETWORK` 选择 `product.*.json`：
   `internal` / `ioa` → `product.internal.json` / `product.ioa.json`；
   `internet` → `product.json`
3. 与服务端结果**合并**，同 ID 时以 `/v3/config` 为准（它有 `supportedEfforts`）
4. 只采纳 `supportsToolCall !== false` 且出现在静态表 `models` 中的条目
5. 本地表缺 `supportedEfforts` 时，`thinkingLevelMap` 留空或从 `effort` 单挡推断
