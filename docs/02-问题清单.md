### #6 refresh token 请求头用错

**严重度：严重。** 影响三条刷新路径全部失效，token 过期后只能重新登录。

`src/auth-flow.ts::refreshAccessToken` 当前实现：

```ts
{ method:"POST", headers:{ "Content-Type":"application/json", Accept:"application/json",
    Authorization:`Bearer ${refreshToken}` }, timeoutMs: REFRESH_TIMEOUT_MS }
```

opencode 版在 `8c52c4c` 已修复为：

```ts
{ method:"POST", headers:{ "Content-Type":"application/json", Accept:"application/json",
    "X-Refresh-Token": refreshToken, "X-Auth-Refresh-Source": "plugin" }, timeoutMs: REFRESH_TIMEOUT_MS }
```

**真实端点对照（2026-10-11 实测，`copilot.tencent.com`，假 token）：**

```
Authorization: Bearer <token>  → 400 {"code":10001,"msg":"10001:refreshToken is empty"}
X-Refresh-Token: <token>       → 401 {"code":12153,"msg":"refresh token failed:10000:token format error"}
```

服务端**完全不读 `Authorization`**，直接判定 refreshToken 为空。后者返回的
「token format error」证明服务端确实读取了 `X-Refresh-Token`。

**受影响路径**（均调用 `refreshAccessToken`）：

1. `src/index.ts` 的 `oauth.refreshToken`（Pi 原生 5 分钟 skew 预刷新）
2. `src/index.ts` 的 `refreshAndPersist`（auth-fetch 流中途 401 兜底）
3. 上述两条链路的下游

**已确认无 PR 覆盖**：grep 三个 PR 的完整 diff，`X-Refresh-Token` 出现 0 次，
`auth-flow.ts` 未被任何 PR 触及。

**修复**：按 opencode 版改写请求头，并补回归测试（断言 `X-Refresh-Token` 存在、
`Authorization` 不存在、透传轮换后的 `refreshToken`）。

### #3 `reasoning_content` 兜底缺失（上游 11155）

opencode 版在 `auth-fetch.ts` 遍历 messages，为缺字段的 assistant 消息补 `reasoning_content: ""`：

```ts
if (Array.isArray(parsed.messages)) {
  for (const m of parsed.messages) {
    if (m?.role === 'assistant' && m.reasoning_content === undefined) m.reasoning_content = ''
  }
  body = JSON.stringify(parsed)
}
```

背景：带 `tools` 的请求要求历史 assistant 回传 `reasoning_content`（否则上游 400 `code 11155`）；
但部分模型可跳过推理（`canDisableThinking`），此时无内容可回传。

pi 版**既未做 body 注入，也未设 `compat` 开关**。

**更优方案**：pi-ai 已有原生开关 `compat.requiresReasoningContentOnAssistantMessages`
（`api/openai-completions.js:1047`），无需手工改 body。注意它依赖 `model.reasoning === true`，
因此必须与 #2 一起修才有意义。

**待定**：设该 compat 即可，还是两者都保留（与 opencode 的「两层都留」策略一致）。

### #4 `thinkingLevelMap` 语义用反

当前实现（`src/models.ts::remoteModelToPi`）：

```ts
const effort = m.reasoning?.defaultEffort ?? m.reasoning?.effort
const efforts = m.reasoning?.supportedEfforts
if (cfg.reasoning && efforts?.length) {
  cfg.thinkingLevelMap = Object.fromEntries(efforts.map((e) => [e, e])) // 键用上游档名
  if (effort) cfg.thinkingLevelMap.default = effort // "default" 不是合法键
}
```

对照 pi-ai 契约（见《现状与上游调研》§6.2）：

- `thinkingLevelMap` 的键必须是 `off|minimal|low|medium|high|xhigh|max`；
  用上游档名（如某些模型只给 `high`/`xhigh`）作键可能成为死键
- `default` 不是合法键，当前写法无效
- `xhigh`/`max` 必须在 map 中有条目才在 UI 可见
- 不支持的档位应以 `null` 显式标记

**上游真实档位分布**（实测 `/v3/config`，craft agent 13 个模型）：

| 模型                                                | `supportedEfforts`                               |
| --------------------------------------------------- | ------------------------------------------------ |
| `deepseek-v4.1-flash` / `glm-5.3` / `glm-5.3-flash` | `low` / `high` / `max`                           |
| `space-bunny`                                       | `low` / `medium` / `high` / `xhigh` / `max`      |
| `deepseek-v4-pro`                                   | `low` / `high` / `xhigh`                         |
| `glm-5.2`                                           | `high` / `xhigh`                                 |
| `hy3` / `hy3-x`                                     | `low` / `high`                                   |
| `hy4-preview-f`                                     | `high`                                           |
| `auto` / `glm-5.1` / `kimi-k3-1` / `minimax-m3`     | 无 `supportedEfforts`（仅有 `reasoning.effort`） |

**注意**：PR #4 对这块仅加了「无 `supportedEfforts` 时设 `supportsReasoningEffort: false`」，
未修正键的语义。此问题在三个 PR 中均未被解决。

**待定**：重做策略（仅映射上游真实存在的档位、不支持的设 `null`、默认档如何表达）。
